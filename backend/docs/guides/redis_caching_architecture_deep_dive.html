The "Feel": Why Does Redis Feel Instant?

Understanding physical storage latency differences between RAM and Database Disks.

❌ PostgreSQL Query (Without Cache)

1. Express sends TCP query over socket.
2. DB parses SQL, planner runs analysis.
3. Joins Category, Template, and User tables.
4. Disk I/O read operations from NVMe / SSD.
5. Serializes rows into JSON and returns over network.
⏱️ Latency: ~50ms to 250ms under concurrent load.

✅ Redis Cached Read (RAM)

1. Express checks Redis key (e.g. cache:categories:all).
2. Redis is pure in-memory Key-Value C-engine (RAM).
3. O(1) hash table lookup.
4. Returns pre-serialized JSON string directly.
5. No SQL parsing, zero disk read, zero joins.
⚡ Latency: ~0.8ms to 2ms (Over 100x Faster!)

💡 The Golden Rule of Caching:
We only cache data that is read frequently but changes infrequently (Categories, Festival calendar, Master graphic templates, Transparent frame overlay paths, and BrandKit details).

The Cache-Aside (Lazy Loading) Life Cycle

How our getOrSetCache(key, fetcherFn, ttl) orchestrator works under the hood.

Every read request follows a strict 3-phase flow:

Client Request
      │
      ▼
getOrSetCache(key, fetcherFn, ttl)
      │
      ├───► Step 1: Check Redis: redis.get(key)
      │        │
      │        ├──► [HIT]: Return cached JSON immediately! (~1ms)
      │        │
      │        └──► [MISS]: Execute fetcherFn() (Prisma DB Query ~60ms)
      │                 │
      │                 ├──► redis.set(key, data, 'EX', ttl) (Store for next time)
      │                 │
      │                 └──► Return fresh data to Client!

What Happens on Data Updates (Mutation)?

When an admin adds a new Category or user updates their BrandKit, we never wait for TTL expiration. We trigger instant, non-blocking pattern invalidation:

await deleteCachePattern('cache:categories:*');
// Instantly purges list and detail keys so the very next request gets fresh data!
🛡️

Why SCAN and NEVER KEYS * in Production

A critical engineering standard for zero-downtime Redis operations.

❌ The Beginner Mistake: redis.keys('cache:*')

Redis is single-threaded. When KEYS * runs across 500,000 keys, Redis halts ALL incoming read/write operations for hundreds of milliseconds. Causes severe request timeouts and 504 Gateway errors in production!

✅ The Senior Standard: redis.scan(cursor)

Our deleteCachePattern uses cursor-based SCAN in small batches (100 keys per iteration). Redis continues processing API traffic concurrently with zero event loop blocking!

Exact Code Implementation Examples

See how the architecture keeps Controllers thin and Repositories pure while Logic orchestrates caching.

1. Safe Cache Utility Wrapper (src/common/utils/cache.util.js)

export async function getOrSetCache(key, fetcherFn, ttlSeconds = CACHE_TTL.ONE_HOUR) {
  // 1. Try reading from Redis
  const cached = await getCache(key);
  if (cached !== null) {
    return cached; // Cache Hit!
  }

  // 2. Cache Miss: Execute primary DB logic
  const freshData = await fetcherFn();
  if (freshData !== null && freshData !== undefined) {
    await setCache(key, freshData, ttlSeconds);
  }

  return freshData;
}

2. User BrandKit Caching & Invalidation (src/modules/brandkit/brandkit.logic.js)

// Read Operation: Fast 24-hour cache
export async function getBrandKit(userId) {
  const cacheKey = CACHE_KEYS.BRANDKIT_BY_USER_ID(userId);

  return getOrSetCache(
    cacheKey,
    async () => {
      const brandKit = await brandKitRepository.findBrandKitByUserId(userId);
      return sanitizeBrandKit(brandKit || { userId, ...DEFAULT_BRAND_KIT_FALLBACK });
    },
    CACHE_TTL.ONE_DAY
  );
}

// Write Operation: Immediate Purge
export async function updateBrandKit(userId, payload, fileBufferOrFiles) {
  // ... image uploads & Prisma upsert ...
  const updated = await brandKitRepository.upsertBrandKitByUserId(userId, dataToSave);

  // Invalidate cache immediately
  await deleteCachePattern(CACHE_KEYS.BRANDKIT_PATTERN(userId));

  return sanitizeBrandKit(updated);
}
